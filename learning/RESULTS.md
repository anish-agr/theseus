# ML lane results

Every number on this page was produced on the Windows dev machine (CPU
only) and is reproducible with the commands shown. Trained weights live
in gitignored `runs/` directories; the scripts that made them are
tracked, so the honest unit of reproducibility here is "same command,
same seeds, same numbers".

## Lane A — monocular depth → occupancy (real footage)

Validated on **TUM RGB-D `fr1_desk`** — real handheld video with
motion-capture ground-truth poses, i.e. exactly what ARKit will provide
on-device (frames + trusted poses), minus Apple hardware.

| check | result |
|---|---|
| camera-track cells wrongly marked occupied | **0 / 133** |
| camera-track cells recovered as FREE | **130 / 133** (3 unknown) |
| map quality | coherent metric floor plan of the desk scene ([screenshot](../docs/media/depth-tum.png)) |

Method notes that turned out to matter:

- Monocular depth is **affine in *inverse* depth**: per frame, fit
  `1/z = s·r + t` against sparse metric anchors (`run_depth.py
  --sparse`). The mocap poses play the role ARKit feature points will
  play on-device. Fitting in depth instead of inverse depth looks fine
  on a wall and falls apart on a corridor.
- TUM's mocap frame is z-up (asserted, not assumed) and rolled frames
  are filtered out — roll is the one axis our `CameraPose` doesn't
  model, so it's the no-go axis rather than a silent error source.
- Measured limit: floor-ray placement **overshoots elevated objects**
  (desk monitors landed 3–5 m past their true spot). The fix is
  depth-at-box fusion, scheduled with the on-device work (M4). Written
  down so nobody mistakes the current behavior for correct.

```
python learning/tum_prep.py --seq <fr1_desk dir>     # poses -> our format
python learning/run_depth.py --video <clip> --model learning/models/depth_anything_v2_small.onnx --sparse ...
```

Synthetic regression (no ML deps, runs in CI): `demo_depth.py` renders
an analytic room, runs the identical geometry, and asserts the
recovered map — 50 frames, floor-fit max error 0.45 m at the far wall,
golden-hashed.

## Lane B — detection → named waypoints (real footage)

YOLO11n over public clips (Pexels kitchen/dining, TUM office), boxes
floor-projected and pushed through the merge/promote/decay registry:

| clip | promoted waypoints | ghosts |
|---|---|---|
| kitchen (Pexels) | fridge, two ovens | 0 |
| dining room (Pexels) | table, chairs | 0 |
| office (TUM fr1_desk) | monitors, chair | 0 |

The registry's promote threshold does the anti-ghost work: a proposal
needs repeated consistent sightings before it becomes a waypoint, so
single-frame hallucinations die by decay. Same elevated-object caveat
as Lane A (it's the same floor-ray geometry).

```
python learning/run_detect.py --video <clip> --height 1.40 --pitch 0.5
```

## Lane C — PPO steering vs the scripted baseline

PPO (stable-baselines3) over `NavEnv` — a Gymnasium env whose
kinematics, collision checks and movers are the engine's own tested
simulator. Curriculum with warm starts: static → 1 mover → 3 movers.
Held-out = seeds 1000–1029, disjoint from training, evaluated by
`evaluate.py` (success rate + SPL, Anderson et al. 2018).

| stage | learned success / SPL | baseline success / SPL |
|---|---|---|
| static clutter | **0.90 / 0.85** | 0.60 / 0.60 |
| 1 mover | **0.90 / 0.86** | 0.37 / 0.37 |
| 3 movers | **0.87 / 0.73** | 0.30 / 0.30 |

The headline isn't the absolute numbers — it's the trend: **the
learned policy's edge grows as the world gets more dynamic** (+0.30 →
+0.53 → +0.57 success). Reactive local steering around moving people
is precisely where hand-tuned VFH gives up first.

Deployment is proven, not promised: `export.py` exports each stage to
a **78 KiB ONNX** graph and verifies it two ways — 256/256 identical
argmax actions vs SB3 on real observations, then full held-out
episodes driven by onnxruntime (success/SPL reproduce the table above
exactly). Core ML conversion at M5 starts from these .onnx files.

Known limit: everything above is measured **in simulation** — held-out
procedural rooms, the engine's own kinematics. On-device behavior
against real pose noise and real clutter is unmeasured until the M5
integration; the numbers claim sim performance, nothing more.

```
python learning/rl/train.py --stage movers1 --init learning/rl/runs/ppo_static
python learning/rl/export.py --stage movers3 --episodes 30
```

## Lane D — map inpainting UNet

Small UNet (partial occupancy in, full occupancy out), training pairs
generated by running the sim's limited-FOV sensor over procedural
floorplans. Held-out rooms:

| metric | UNet | nearest-known baseline |
|---|---|---|
| cell accuracy | **0.844** | 0.770 |
| IoU (occupied) | **0.587** | 0.388 |

Strictly advisory by policy: predicted cells are never traversable —
the world model's "unknown is a wall" rule outranks any network. The
use case is prioritizing frontier exploration and prettier previews,
not routing humans through guessed space.

Known limit: train and held-out rooms both come from the same
procedural floorplan generator. Accuracy on real scanned rooms is
unmeasured; treat the numbers as generator-domain results.

```
python learning/inpaint/train_unet.py
```
